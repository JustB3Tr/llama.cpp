# First hardware observations

2026-11-17, RTX 4060 8 GiB, i7-11700K, WSL2 Linux 6.6.114.1, ~39 GiB WSL RAM. DeepSeek V4 Flash Q2_K_S, two GGUF shards totaling 98,592,510,368 bytes, read through `/mnt/d`. Existing local tandem server built from llama.cpp f5222f25c plus the local tandem patch was used, not a newly compiled binary from this branch. Each row is one request with an 11-token prompt, 12 requested output tokens, context 1024, prompt cache disabled, greedy temperature, and 8 CPU threads. Both used `-cmoe --moe-cache-mib auto`.

| GPU layers | Startup | Prompt | Decode | Process read_bytes during request | Observation |
|---:|---:|---:|---:|---:|---|
| 99 | 69.1 s | 0.261 tok/s | 0.436 tok/s | 20,080,005,120 | Explicit warning: fewer than 256 MiB available, MoE cache disabled |
| 10 | 46.1 s | 0.289 tok/s | 0.407 tok/s | 19,790,413,824 | No cache-disabled warning, but logging was insufficient to prove cache activation |

This is a diagnostic pair, **not a valid speedup claim**: the second run followed the first without controlling the OS page cache; one tiny request per configuration is noisy; GPU layer placement changes computation; process read bytes include prompt and decode and are not verified physical device bytes. The generated text differed, so token equivalence has not been demonstrated. A normal chat prompt, longer generation, activation logs, and alternating repetitions are needed. Previous user-reported Windows and WSL results used different setups and cannot be treated as controlled comparison.

The server reported `failed to fit params ... n_gpu_layers already set by user`; both layer settings were explicit. At 99 layers it also warned that the MoE cache was disabled, even though VRAM was nearly full. Thus VRAM occupancy alone did not prove an expert cache existed. The warning establishes this run's state only; it does not establish the earlier run's state. At 10 layers the absence of the warning is not positive proof of a working cache.

Raw `result.json` and `server.log` for both runs were retained outside the repository on the test machine in `C:\projects\llama-lowram-bench`. They include local file paths. Subsequent trials should raise log verbosity and/or use tandem's `LLAMA_MOE_STATS_FILE` to confirm the cache and measure hit/read counters, then test exactness with identical prompts and deterministic settings. Record competing Windows disk activity separately.

The five focused Python tests passed under WSL. The modified `llama-moe-cache.cpp` also compiled independently with the local C++ compiler and the CUDA-enabled build's preprocessor definitions; that is a compilation check, not an inference or performance test.

## Mixed-build smoke test

To exercise the modified source while the full clean CUDA build was incomplete, the modified cache source was compiled independently and linked with objects from the existing tandem build into a separate `libllama.so`. The existing tandem server and other shared libraries were used with this replacement library via `LD_LIBRARY_PATH`. This is a mixed build, not a clean reproducible build of the whole branch. `LLAMA_MOE_FAULT_AUTO=0` was set, and `-lv 4` and `LLAMA_MOE_STATS_FILE` captured activation and counters.

With the same model, prompt, 12 requested tokens and `-ngl 10`, startup was 39.1 s, prompt 0.279 tok/s and decode 0.434 tok/s. The server reported a 3,811.5 MiB GPU expert cache for nine layers, 482 slots and 18,144 MiB of host experts; stats recorded both hits and misses. The generated 12-token text matched the earlier 10-layer run. The earlier original 10-layer run measured 0.407 tok/s, but these single sequential runs have uncontrolled page cache state, different fault-auto settings, and mixed-build provenance, so the difference is not a measured improvement. This 10-layer case did not log automatic RAM store activation and therefore does not validate the store-selection fix. Logs and stats are in the local `fork-hybrid-10layers-01` directory next to the earlier logs.

At `-ngl 20`, the same mixed build reported a 2,307 MiB GPU cache and 38,304 MiB of host experts. Startup was 53.2 s, prompt 0.277 tok/s and decode 0.437 tok/s; its short generated text matched the 10-layer mixed run. It also did not report automatic RAM store activation. These values are one sequential trial, not a speedup or quality evaluation.

At `-ngl 25` with `LLAMA_MOE_FAULT_AUTO=0`, the mixed build reported 1,567 MiB GPU cache for 24 layers and 48,384 MiB of host experts. It activated store mode and allocated a 36,077 MiB CUDA-host arena with direct reads. The request took 54.3 s: prompt 0.329 tok/s and decode 0.528 tok/s, with 9,069,096,960 process read bytes during the request. On shutdown, the cumulative arena log (which includes warmup) reported 673 hits, 1,504 reads, 11.6 GiB read and no failed placements. The arena allocation is a substantial memory commitment, not free RAM.

The original tandem build was then run with the same 25-layer flags and fault-auto setting. It logged the same cache capacity but no store-mode or arena initialization, supporting the targeted behavioral fix. It measured prompt 0.296 and decode 0.442 tok/s, with 19,809,091,584 process read bytes during the request; the returned short text matched the mixed build. These numbers are an ordered, unreplicated diagnostic, with a mixed build, uncontrolled OS cache and different storage paths; the process counters are not verified physical device I/O. They cannot establish the magnitude or cause of a speed difference, nor comprehensive output equivalence. The raw logs and per-second cache statistics are in `fork-hybrid-25layers-01` and `original-25layers-01` on the test machine.

## Clean CUDA build

A full CUDA Release build of this branch completed successfully with CUDA 13.4, GCC 15, CMake, `CMAKE_CUDA_ARCHITECTURES=89`, and `LLAMA_CURL=OFF`. It was built before the subsequent documentation-only commits. On the same machine the clean fork server, with the same 25-layer settings and `LLAMA_MOE_FAULT_AUTO=0`, reported store mode active, a 36,174 MiB CUDA-host arena and a 1,567 MiB GPU cache. Startup was 49.1 s, prompt 0.348 tok/s, and decode 0.554 tok/s; the 12-token text matched the original and mixed 25-layer runs. The request reported 9,064,611,840 process read bytes. The same uncontrolled-cache and short-run limitations apply, so this is a functionality check, not proof of a speedup. Raw files are in `fork-clean-25layers-01`.

For this machine, the clean build's WSL executables and shared libraries were copied to `/mnt/c/projects/llama-lowram-bin`. The build has an absolute original library search path, so set `LD_LIBRARY_PATH=/mnt/c/projects/llama-lowram-bin` when running this copy. The copied server's `--version` was checked. For a fresh build, configure from this repository with `cmake -S . -B build -DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=89 -DCMAKE_BUILD_TYPE=Release -DLLAMA_CURL=OFF` and build `llama-server`; the CUDA compiler must be on PATH or supplied via `CMAKE_CUDA_COMPILER`.
